# CPAMP 日志页可读性改版设计

状态：已完成视觉方向确认，待用户审阅书面设计

日期：2026-08-07

## 背景与证据

当前桌面 App 通过 CPAMP Manager Plus 提供管理页。Codex Auth 固定安装 CPAMP `v1.11.11`，管理页由 CPAMP 二进制内置的 Web 前端提供，地址为 `http://127.0.0.1:18317/management.html`。

截图和源码核对得到三个明确问题：

1. 日志页在矮视口媒体查询下给筛选区设置了 `max-height` 和 `overflow: auto`，导致上半区出现独立滚动条；用户需要在筛选区和日志区之间来回滚动。
2. 路径筛选把完整 URL 路径和查询参数直接铺成大量标签，信息密度高但缺少语义；完整路径对普通用户没有持续可读价值。
3. `/v0/management/latest-version` 等管理后台轮询请求与模型请求混在一起。管理接口的 502 会被误认为模型请求失败，日志页因此显得嘈杂。

CPAMP 已有“请求监控”页承担统计和业务分析职责；本设计只优化“日志查看”页的快速排障体验，不把日志页重新建设成第二个监控中心。

## 目标

- 筛选和操作区域固定，不产生独立的纵向滚动；纵向滚动只发生在日志列表。
- 默认日志行只展示用户能立即理解的四类信息：状态、时间、业务语义、耗时。
- 默认隐藏管理后台日志，并以低干扰提示说明隐藏数量；用户可临时恢复查看。
- 点击或展开单行后，仍可查看完整 HTTP 方法、路径（含查询参数）、来源、IP、源码位置、请求 ID 和原始日志复制入口。
- 明确区分模型请求失败与管理请求失败，避免把后台轮询 502 误报成模型转发故障。
- 保留现有搜索、状态/方法/路径筛选、原始日志模式、增量刷新、下载和错误日志标签页能力。

## 非目标

- 不修改 CPA 的路由、代理、TUN 或 502 处理逻辑。
- 不修改请求监控数据模型、用量统计或错误日志 API。
- 不删除或改写原始日志；任何解析失败都必须保留原文。
- 不在 Codex Auth Swift 代码中复制一套管理页 UI。
- 不通过运行时注入 CSS/JavaScript 的方式覆盖第三方二进制资源。

## 用户界面设计

### 1. 固定控制区

日志卡片分成“固定控制区”和“日志列表”两层。固定控制区包含：

- 搜索框：搜索请求、状态码或错误摘要。
- 状态快捷筛选：全部、失败、慢请求；保留现有状态分组筛选作为“更多筛选”中的选项。
- “更多筛选”按钮：打开弹层或抽屉，承载请求方法、状态分组和路径选项；不把多行路径标签直接撑开主页面。
- 刷新和更多操作按钮。
- 一行低干扰状态提示，例如“已隐藏 9,901 条后台管理日志 · 临时显示”。

控制区不设置 `overflow: auto`。在桌面和矮视口下都保持自然高度；只有日志列表容器拥有固定可用高度和纵向滚动。

### 2. 默认日志行

每行使用固定的轻量网格：

| 区域 | 默认内容 |
| --- | --- |
| 时间 | `HH:mm:ss`，必要时保留日期 |
| 状态 | 2xx/3xx/4xx/5xx 状态徽章，颜色只表达严重度 |
| 摘要 | 语义化事件名称，例如“模型请求成功”“后台版本检查失败” |
| 次要信息 | 产品或接口类别，例如 `Responses API`、`版本检查` |
| 耗时 | 规范化延迟，如 `84ms` |
| 操作提示 | 展开箭头；双击复制原始行的行为继续保留 |

成功行保持低对比度；4xx/5xx 行使用左侧色带和状态徽章突出显示。状态颜色不替代文字，不依赖色觉判断。

### 3. 语义分类

在现有 `parseLogLine` 之后增加纯函数分类层，分类失败时使用保守的“HTTP 请求”或“请求失败”摘要，不猜测上游原因。

首批分类：

- `/v1/responses`、`/v1/chat/completions`、`/v1/completions`、`/v1/embeddings`：模型请求。
- `/v0/management/latest-version`：版本检查。
- `/v0/management/usage-queue...`：用量读取。
- `/v0/management/auth-files...`：账号配置读取。
- 其他 `/v0/management/*`：后台管理请求。
- 其他可解析 HTTP 行：HTTP 请求；无法解析：原始日志。

对于管理路径的失败摘要，可以明确说明“管理请求失败，不代表模型请求失败”；对于模型路径不能从单条网关日志推断具体上游原因，只显示实际状态和原始消息。

### 4. 展开技术详情

展开行显示完整技术信息，不改变日志原文：

- `METHOD path?query`
- 客户端 IP、请求 ID、耗时和状态码
- 日志源文件/行号（如存在）
- 复制原始日志
- 按同类路径筛选

完整路径不再常驻在筛选标签或默认行中，但永远可通过展开区域、悬浮提示和原始日志模式取得。

### 5. 默认过滤策略

- 首次使用默认屏蔽 `/v0/management`，并兼容已有本地存储值；用户主动关闭后尊重其选择。
- 不删除被屏蔽日志，只在展示层过滤；下载原始日志的语义保持现有行为并在界面上明确“下载全部缓冲日志”。
- 原始日志模式作为高级操作保留，打开后可横向滚动和复制多行文本，但不改变默认结构化视图。

## 组件与数据流

```text
原始日志行
    -> parseLogLine（时间、状态、方法、路径、延迟等结构化字段）
    -> classifyLogEvent（模型/管理/未知 + 语义摘要 + 影响提示）
    -> useLogFilters（搜索、状态、方法、路径）
    -> LogRow（折叠摘要）
    -> LogRowDetails（完整路径、原文和复制操作）
```

`classifyLogEvent` 必须是无副作用的纯函数，便于针对路径、状态和未知输入编写单元测试。`LogRowDetails` 只接收已经解析的单行对象，不重新请求后端。

## 实现归属与发布方式

日志页源码位于 CPAMP 上游仓库 `apps/web/src/features/logs/`，不是 Codex Auth 仓库的一部分。Codex Auth 的职责是：

1. 固定 CPAMP 版本、下载地址和 SHA-256。
2. 安装并健康检查 CPAMP。
3. 在文档中记录兼容的管理页版本。

因此正式实现应在 CPAMP 源码（上游或维护中的 fork）完成并生成新版本，再在 Codex Auth 中更新 CPAMP 版本与校验值。禁止在安装后直接修改二进制或向管理页注入脚本；这种方式不可复现、无法通过完整性校验，也会在下一次安装时丢失。

若没有可发布的 CPAMP fork/release 权限，本次可以先完成 CPAMP 侧补丁、测试和构建验证，但不能宣称 Codex Auth 的桌面安装包已经包含该 UI 变更。

## 错误处理与兼容性

- 解析失败时保留 `raw`，摘要使用“原始日志”，不阻塞整页渲染。
- 未知路径不显示未经证实的“模型失败”或“服务不可用”结论。
- 旧版本 API 缺少某个字段时，详情区域隐藏缺失字段，默认行仍可渲染。
- 分类映射只影响展示，不影响现有筛选值、下载内容或后端请求。
- 管理日志隐藏数量来自当前缓冲区，使用“当前缓冲区”措辞，避免暗示数据库总量。

## 验证方案

CPAMP 源码侧：

- 分类函数单元测试：模型路径、管理路径、查询参数、未知路径、502 和解析失败。
- 日志页组件测试：控制区无内部滚动、管理日志默认隐藏、展开详情包含完整路径、原始日志复制入口存在。
- `npm run type-check`、`npm run lint`、相关 Vitest 测试和 `npm run build`。

Codex Auth 集成侧：

- 更新安装器版本和 SHA-256 后运行脚本的健康检查。
- 验证 CPAMP 管理页资源完整性检查仍通过。
- 使用真实桌面 App 打开管理页，确认默认只滚动日志列表，且管理接口 502 不再混入默认模型排障视图。

## 交付边界

本设计获批后，下一阶段先在 CPAMP 源码中实现并验证 UI；只有拿到可复现的新 CPAMP release 后，才更新 Codex Auth 的安装器和兼容文档。任何外部仓库 push、release 发布或桌面重新安装都需要单独确认。
